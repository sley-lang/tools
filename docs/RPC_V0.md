# Local RPC v0

`sley-tools rpc --project PROJECT_DIR` serves newline-delimited JSON-RPC 2.0 on stdin/stdout. The process is scoped to that one local project. It starts one native builder worker when the workspace is opened and keeps that worker for repeated calls. Closing stdin stops both processes. The backend validates the project and pins its accepted state root; an edit during the session returns `ST_STALE_BASE` until the caller starts a new session. `workspace.open` after worker loss starts a fresh worker and rotates the opaque handle.

The default methods are `sleytools.hello`, `sleytools.workspace.open`, `sleytools.program.inspect`, `sleytools.program.execute`, `sleytools.tests.run`, `sleytools.program.propose`, `sleytools.candidate.validate`, `sleytools.candidate.commit`, `sleytools.candidate.discard`, `sleytools.operation.status`, and `sleytools.operation.cancel`. An explicitly scoped workspace adds `sleytools.artifact.export`, `sleytools.artifact.import`, and `sleytools.review.compare` as described below. Other method names return `ST_FEATURE_UNSUPPORTED`. The execution adapter accepts the `evaluate` entrypoint of Release Readiness, Resource Admission, and locally authored `graph_v0` projects. Release Readiness takes `test_run_completed: Boolean`, `tests_failed: u32`, `artifact_verified: Boolean`, and `blocking_findings: u32`. Resource Admission takes requested/available workers and memory in MiB as nonnegative `i64`. Both return tagged native records. Graph projects take `{ "kind": "arguments", "values": [...] }` in recipe parameter order; each value is a tagged Boolean, `u32`, or `i64`. The response is a tagged primitive or record matching the accepted graph result. All responses bind the root and function and include observation, value hash, profile, instruction count, worker PID, and elapsed RPC dispatch time in separate metadata. A computed `allow=false` is a successful invocation.

For portable package operations, start `sley-tools rpc --project PROJECT --workspace WORKSPACE`. `PROJECT` must already be a direct child of the real `WORKSPACE` directory, and that directory must not be writable by group or other users. The selected project's trusted local core configuration supplies the exact pinned core; request arguments cannot substitute a binary or arbitrary filesystem path. Call `workspace.open` first and use its handle. Package and destination names are 1–64 ASCII letters, digits, underscores, or dashes, starting with a letter or digit; they designate direct children of `WORKSPACE`.

| Method | Parameters after `workspace.open` | Result |
|---|---|---|
| `sleytools.artifact.export` | `{handle, package:"before"}` | Creates a new portable package directory with manifest, native artifact, and graph recipe when applicable; reports their hashes and the unchanged accepted root. External assertions execute during export and may persist reports. |
| `sleytools.artifact.import` | `{handle, package:"before", destination:"replay"}` | Verifies the package manifest and native artifact, imports through the selected core into a new direct-child project, and returns the native import and assertion result with an operation ID. A repeat of the same verified request reconciles the recorded result; an unrelated existing destination is refused. |
| `sleytools.review.compare` | `{handle, before:"before", after:"after", cases:CASE_DOCUMENT}` | Reimports both verified packages under the selected core, checks the supplied baseline cases, and returns the bounded exact-identity Review report. `CASE_DOCUMENT` uses the existing Release Readiness, Resource Admission, or graph case contract. |

These methods are absent from `hello.methods` without `--workspace`. Export leaves the selected accepted root unchanged, but it creates a separate package. Import and Review can take longer than a scalar call because they construct fresh native workspaces and run the declared cases. Import records its operation ID, package and artifact hashes, destination, and pinned core hash in `.rpc-import-DESTINATION.json` before attempting construction. After a lost reply, repeat the same request: a verified completed destination returns the recorded result with `reconciled: true`, without another import. An unfinished destination that cannot be verified returns `ST_COMMIT_OUTCOME_UNKNOWN`; inspect the named destination and operation record before further action. Review returns a report to the caller; use the CLI `review` and `review verify` commands when a saved report is required. The scoped RPC probe covers graph and Release Readiness packages, edited behavior, import/replay recovery, exact Review changes, tampering, symlinks, invalid names, and the unscoped refusal.

The authoring methods expose the [bounded native lifecycle](AUTHORING_V0.md) for one field in each program. `program.propose` takes `handle` and `change: {field, value}` for the worked programs. Release Readiness accepts `max_blocking_findings` with a tagged `u32`; Resource Admission accepts `require_memory_spare` with a tagged Boolean. A graph project accepts `change: {field:"constant.NAME", value:TAGGED_VALUE, cases:GRAPH_CASES}` for an existing named constant, or `change: {field:"operation.BLOCK.NAME.opcode", value:"less_than", cases:GRAPH_CASES}` for a compatible targeted opcode replacement. `GRAPH_CASES` is a `sley-tools.graph-cases.v0` document containing expected postchange behavior. The response contains the exact `candidate_id` and `base_root`. `candidate.validate` takes that ID, runs the selected core's candidate validation, and returns a durable tools `operation_id` bound to the workspace, candidate, and expected parent. `candidate.commit` requires a separately validated, still-current ID, records `commit_requested` before contacting the core, revalidates the same candidate, and returns `sley-tools.rpc-commit.v0` with the operation ID, commit receipt, and new root. A successful commit closes the old worker and invalidates the old handle; call `workspace.open` to get a new handle and worker at the new root. Graph `commit.postcommit_assertions_status` and the response's `external_assertions` are `PASS` or `FAIL`; a false expectation can fail after a native commit has succeeded. The response still supplies the accepted new root. `candidate.discard` drops a pending proposal without changing the accepted root. All four methods reject stale sessions and serialize project writes. Python `Program` and TypeScript `Program` expose `propose`, `validate`, `commit`, and `discard`; their `commit` methods reopen and refresh the program automatically. On commit transport loss, the SDKs query durable operation status; an unresolved outcome returns `ST_COMMIT_OUTCOME_UNKNOWN` with the operation ID and preserved project path.

`sleytools.operation.status` takes `{ "operation_id": HEX }` and checks the durable operation record against the core's verified candidate receipt ancestry. It works even if the core committed but local manifest/state files were not updated before a crash. A matching verified receipt reports `completed`; absence after `commit_requested` reports `outcome_unknown`, never permission to retry. The CLI equivalents are `sley-tools operation status --project PROJECT --id HEX` and `sley-tools reconcile --project PROJECT --candidate-id HEX --expected-parent HEX`.

`sleytools.operation.cancel` takes the same operation ID. Under the project write lock it records `cancelled_before_commit` only while the operation is still validated; both RPC and CLI commit then refuse that candidate. Once commit was requested, it records `cancel_requested` and leaves the outcome to receipt reconciliation. A completed commit stays `completed`. Concurrent cancellation cannot preempt an in-flight locked write in this profile; a busy lock returns `ST_RESOURCE_LIMIT`. The CLI equivalent is `sley-tools operation cancel --project PROJECT --id HEX`; SDK runtimes expose `operation_status` / `cancel_operation` in Python and `operationStatus` / `cancelOperation` in TypeScript.

On commit transport loss, Python and TypeScript query the operation ID using the CLI independently of the prior RPC process. A verified receipt is reported as a completed commit requiring reopen or repair; an unresolved outcome remains `ST_COMMIT_OUTCOME_UNKNOWN`. For SDK-imported artifacts, close preserves the temporary project after either outcome and the error names its path and operation ID. Keep that project until reconciliation is complete.

Integer wire values use canonical decimal strings: `{ "kind": "integer", "type": "i64", "value": "9007199254740993" }`. Boolean values use `{ "kind": "boolean", "value": true }`. Resource Admission returns its requested and available memory values as exact tagged `i64` fields. Python exposes them as `int`, and TypeScript as `bigint`. JavaScript accepts only safe integral numbers or `bigint` as inputs; Python rejects `bool` as an integer. Absent or extra record fields and coercions fail with `ST_INPUT_INVALID`.

For graph projects, Python `Runtime.open_project(PROJECT)` returns a `Program` whose `call('evaluate', inputs=...)` takes a map keyed by parameter names. TypeScript `Runtime.openProject({ project: PROJECT })` returns a `Program` with a typed `callGraph('evaluate', { inputs })` method. Python uses `int` for both integer types. TypeScript accepts safe numbers or `bigint` and returns signed 64 bit values as `bigint`. The SDKs validate the exact parameter set and tag values before RPC. Both expose named constant and compatible opcode edits: Python `program.propose_graph_constant(...)` or `program.propose_graph_opcode(block, name, opcode, cases)`, and TypeScript `program.proposeGraphConstant(...)` or `program.proposeGraphOpcode(block, name, opcode, cases)`. Each case has `{id, inputs, expected}` with named host values; the SDK maps it to the graph case contract and checks exact types. Then use `validate(candidate_id)` and `commit(candidate_id)`. The SDKs can initialize a fresh project from a recipe object and cases via `create_graph` or `createGraph`; Python `GraphBuilder` and TypeScript `GraphBuilder` assemble that recipe without hand-written JSON. Those methods call `sley-tools init` before starting RPC. The worker snapshots the bound graph recipe, verifies the accepted function signature, executes the Sley VM, and checks the exact result shape. Artifact transfer through SDKs is not yet part of this profile.

Requests and responses are limited to 64 KiB and 256 KiB respectively, nesting depth to 16, one request in flight, and execution deadline to 60 seconds. Duplicate JSON fields, unknown fields, and malformed tagged values are rejected. A deadline kills the native worker and returns `ST_RESOURCE_LIMIT`; worker loss returns `ST_TRANSPORT_FAILED`. Errors carry `data.tools_code`, `data.category`, and available core diagnostics. Stdout carries protocol frames only. `tests.run` reports external assertions separately from native test admission; the latter remains pending a production core executor.

Read-only SDK calls accept cancellation through Python `Program.call(..., cancel_event=threading.Event())` and TypeScript `Program.call(..., {signal: AbortSignal})` or `callGraph` with the same option. A signal set before dispatch returns `ST_CANCELLED` without closing the session. Cancelling an in-flight call stops the process group containing the local RPC process and native worker, returns `ST_CANCELLED`, and requires opening a new runtime for later calls. This local SDK control is separate from the RPC operation cancellation described above. It does not assert that a completed read was rolled back.

Artifact import creates a fresh local workspace. Native read execution can persist an execution report in that workspace, so artifact invocation is not storage free. No daemon or machine-wide cache is started. The current elapsed measurement includes RPC dispatch through the native result; encoding, decoding, and core VM time are not separately measured. This profile is local and versioned as `sley-tools.rpc.v0`.

The checked-in [bounded soak evidence](../evidence/bridge/soak-v2.json) runs 256 varied Release Readiness calls through each SDK after warmup. The client, RPC process, and native worker retained constant file descriptor counts at 64-call intervals, one worker handled each matrix, and both child processes exited on close. This is a local Linux measurement for the selected artifact, not a general lifetime or workload guarantee.

The [Bridge timing report](../evidence/bridge/timing-v4.json) records five fresh opens and 48 checked post-open calls per SDK, including measured throughput, declared RPC limits, and sampled memory. Its backend timer has whole-millisecond resolution and does not isolate VM execution or SDK encoding and decoding. The measurements are local observations, not a cross-language speed ranking.
